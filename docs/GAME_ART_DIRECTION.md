# Game art direction and quality

Each generation runs a structured game-designer and art-director step through the configured OpenRouter coding model before creating imagery or gameplay. A user's explicit theme, style, palette and animation choices take priority. Unspecified choices are inferred for that game's mechanics and audience, with a per-generation creative seed to avoid imposing a single house style. Games do not inherit the host app's black/mint appearance or Neon Comet's theme. The demo remains a separate fixture.

The resulting `GameArtDirection` includes a setting, visual and animation briefs, environment image prompt, quality level, pixel-art rendering flag, typography, corner radius and six safe hex colors. New plans also require a concrete gameplay design (premise, core loop, goal, decisions, progression, feedback and replay); 2D plans require up to four illustrated sprite subjects. Unneeded threat/reward/prop roles are null, keeping deliberately simple games free of invented extra objects. The metadata schema keeps these fields optional only for older source archives. Both artwork and coding receive this same direction. The protected production boot uses the selected colors/type/corners for its menu, HUD and controls; it does not interpolate arbitrary CSS or HTML. The sandbox rejects missing or altered approved direction metadata. Game source and `game.json` are saved together in immutable version source archives.

Premium is the default quality target: the care associated with polished feature animation—expressive shapes, deliberate composition, lighting, materials, depth and coherent motion—within the Phaser mobile renderer. This does not force all prompts into the same 3D-cartoon look. Watercolor, clay, crisp pixel art, hand drawing, realism and other explicit styles remain distinct. Deliberately lower fidelity is selected only when requested; pixel art alone is not lower quality. Modifications preserve the prior style and palette unless a new visual direction is requested.

Premium images request 2K at portrait 9:16 or landscape 16:9. Dedicated Image API endpoints must advertise those capabilities and bounded per-image prices. Muse also supports discovery through its general model catalog when its dedicated endpoint list is empty; this path reserves the full advertised token ceiling and pins the same Muse provider. Its composition/resolution requests are best effort, since that catalog does not advertise dimension capabilities. Assets below 1,024 pixels on their shorter edge are rejected. Normalization preserves aspect ratio, caps the longest side at 2,048 pixels and never upscales or crops the delivered composition. Intentionally low-fi requests use the 1K tier and preserve their simpler output. Every request stays within the reserved generation and daily spending caps.

The coding brief targets 60 FPS with delta-based movement, eased transitions, anticipation/follow-through, appropriate parallax, restrained particles and responsive gameplay feedback. Explicitly requested stepped animation is respected. Browser publication checks test both orientations, console/texture errors, offline network boundaries, controls, nonblank rendering, score UI and a 45 FPS average / 50 ms p95 page-frame performance floor. These are desktop smoke checks; art quality and physical-device performance also require per-game review. Arbitrary gestures cannot solve every puzzle, so positive-score gameplay remains a per-game acceptance check rather than forcing fake timer points into all genres.

## Why foreground graphics looked primitive

The old image path generated only `background.png`. Codex was instructed to create premium characters but had no actual character textures and could edit only gameplay and metadata. Saved live-game source confirms it generated foreground textures from canvas paths and shapes. Phaser 3.90 already supports image sprites and sprite sheets in the existing Canvas renderer; changing engines would not supply the missing art. Vector drawing remains appropriate for effects, shadows, paths, UI and explicitly requested geometric games.

2D jobs now generate a separate 2x2 illustrated sprite sheet matching the game's camera and style: player, threat/challenge, reward and prop. Muse receives a square composition and a solid magenta matte request. Trusted Sharp processing removes the matte connected to the sheet's edges, clears edge spill and preserves enclosed color details. It finds clear horizontal and vertical gutters near the center before cutting, allowing a subject such as a long tail to cross the nominal halfway line. Each gutter can move at most one eighth of the sheet dimension and must leave transparent margins on both sides. Processing trims each subject and packs up to four transparent 512x512 frames into `sprites.png`. Resizing preserves subject proportions and uses nearest-neighbor sampling for pixel art. Missing gutters, empty required frames, unkeyable mattes and clipped subjects receive distinct errors and fail rather than silently falling back to shape-built characters. A malformed sheet gets at most one additional paid image request under the same job accounting and deadline.

The coding brief supplies the exact texture path and frame roles and requires these illustrated assets for the main 2D actors. The browser publication test observes actual Canvas image draws during play in both orientations, rejecting a bundled-but-unused sheet. The sandbox also checks that supplied artwork bytes are included unchanged in the build and source archive. The sprite image has its own immutable checkpoint key, so automatic/manual retries restore it alongside the original background, source and CLI conversation without repurchasing it. A gameplay-only modification reuses the exact prior sprite bytes when subjects, style, palette, pixel-art flag and quality match; a visual or subject change regenerates them. 3D/isometric games retain their mesh-based renderer and do not generate flat sprite sheets.

## Designing play instead of only satisfying controls

The designer plans player actions, consequences and next choices, a readable objective, a forgiving first challenge, genre-appropriate progression and an earned payoff. The coding agent must implement that design as mechanics. Story is tied to player objectives and changes in the world. More undifferentiated spawning, timer-only scoring and increasing speed are not substitutes for variety. Explicit user instructions take priority: a deliberately simple ball tapper stays simple, a cozy game need not acquire enemies, and a modification retains the existing genre, mechanics and save contract. Planning a modification receives bounded prior gameplay source as well as metadata.

These checks establish asset use and functional smoke coverage, not a universal numerical measure of fun or animation quality. Sprite poses currently animate with transforms and tweens; the pipeline does not provide a rigged character or full walk-cycle atlas. Per-game play review and physical-device checks remain necessary.

Configured limit values: GPT-6.1 Sol with high reasoning, $10 per creation/modification job, $100 global per UTC day, 5 creations and 5 modifications per account/day. Enforcement is controlled by the independent switches documented in ENVIRONMENTS.md; protective switches default to enabled for new installations. `pnpm test:generation:live` performs two real creations in contrasting watercolor/clay styles and one modification, verifies signed packages, checks style retention and saves browser screenshots plus cost evidence under ignored `work/live-verification`.

## Visual production and review (2026-10-12)

New plans also require a `presentation` contract: scene composition and relative actor scale, camera, visual hierarchy, five event-specific motion briefs (idle, movement, action, success, failure), and three to six observable acceptance criteria. Gameplay is designed first; artwork and code share the same camera/style. Existing archives without this field remain readable. The current illustrated sheet still supplies static cutouts animated with transforms, not rigged characters or an authored walk-cycle atlas.

Codex now sees the actual supplied background and sprite sheet through a scoped `inspect_art` tool. The trusted host creates small JPEG references without changing the original textures. Only the two named references are readable; arbitrary paths, external image URLs, dependencies and credentials remain unavailable. The Responses gateway preserves bounded image parts instead of flattening them into text. Original artwork bytes remain protected and included in signed packages.

The implementation pass is followed by trusted build and browser checks. The browser captures the menu, early play and later play in portrait and landscape. Production then runs an independent visual review of those six images against the request and presentation contract, using the same configured/billed coding model. Functional success alone no longer publishes a live game. Material visual findings are fed back to the saved Codex conversation for a separate polish/repair pass; the existing repair count, generation deadline and spending accounting bound the loop. Each revised build must pass the functional checks and visual review again. Missing captures, malformed/contradictory approval and unresolved defects fail closed. Provider outages preserve completed coding and paid artwork for review recovery.

Visual review is an AI assessment of static frames, not evidence of animation smoothness, sound quality, fun, App Store approval or physical-device performance. The browser frame sampler still supplies separate desktop performance evidence. This extra review and any polish passes add provider cost and generation time. Existing published games are unchanged; new generations and modifications use the improved pipeline. Deploying requires rebuilding `ai-games-sandbox:1` and restarting the worker; no database migration or mobile rebuild is needed.
