# PostHog analytics

AI Games optionally uses your PostHog project across the API, worker and Expo host app. Telemetry is disabled by default. An application-owned `AnalyticsPort` keeps telemetry out of the domain and generated games. Missing keys disable telemetry; delivery failures cannot fail a game action. Generated packages and agent sandboxes receive no PostHog SDK, credentials or management access.

## Enable and configure

1. Apply `pnpm db:migrate` to install the authoritative account-event outbox.
2. Create your own PostHog project, complete onboarding and choose its plan. No subscription change is made by the setup script.
3. Supply `POSTHOG_CLI_API_KEY` as a **private** management/build environment variable and set `POSTHOG_CLI_PROJECT_ID`. Set `POSTHOG_CLI_HOST` to the project's management region (`https://us.posthog.com` or `https://eu.posthog.com`). The official CLI is included: `pnpm exec posthog-cli login` supports account authorization; the setup script requires an explicit private environment key rather than extracting browser sessions.
4. Run `pnpm analytics:preview`. Inspect `work/posthog/plan.json`, which contains project settings, event definitions and every dashboard query. `POSTHOG_DASHBOARD_ENVIRONMENT` defaults to `production`; set it to `development` for local dashboards.
5. Run `pnpm analytics:configure`. The script checks access to the exact project, anonymizes IP addresses, enables exception processing, documents events and creates two tagged dashboards with 14 insights. It validates each HogQL query on the server before saving it. Repeated runs update tagged objects, preserve unrelated dashboards and event definitions, and avoid duplicate objects.
6. The script writes the project's ingestion token and region to ignored root/mobile `.env` files. Set `POSTHOG_ENABLED=true` and `EXPO_PUBLIC_POSTHOG_ENABLED=true` in the selected private environment files, then restart API, worker and Metro. Deploy the same ingestion key to the server and mobile runtime configuration. Set matching `ANALYTICS_ENVIRONMENT` / `EXPO_PUBLIC_ANALYTICS_ENVIRONMENT` and `APP_RELEASE` / `EXPO_PUBLIC_APP_RELEASE` values for every release.

The public ingestion key (`phc_`) belongs in `POSTHOG_API_KEY` and `EXPO_PUBLIC_POSTHOG_API_KEY`. The private management key must never be `EXPO_PUBLIC_*`, app config `extra`, game source, or a sandbox variable. Use production secret storage for management/build credentials. Setting `POSTHOG_ENABLED=false` or `EXPO_PUBLIC_POSTHOG_ENABLED=false` disables that process. SDK delivery uses bounded queues and buffered requests; ordinary product events are best effort.

## Event semantics and identity

The complete event dictionary is maintained in `scripts/posthog-plan.ts` and applied to PostHog by the setup command. All events include service, environment and release; mobile events also include platform.

| Area       | Captured behavior                                                                                                                                                                                                                                                                                            |
| ---------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| API        | Every response, including health, unauthorized calls, rate limiting and unmatched routes: method, route template, status and server latency. Responses expose `X-Request-ID`; host network events carry that ID for correlation. Successful mutations emit separate events after the action succeeds.        |
| Accounts   | Real auth database insertion, profile/email/confirmation changes, deletion, sign-in/out, accepted signup submissions, recovery and password-update flows. Signup submission is separate from authoritative account creation.                                                                                 |
| Generation | Reservation, live-worker queue delay, preflight, pipeline stages and their durations, validation failure, bounded repairs, publication, terminal failure/cancellation and abandoned-job reclamation. New creation and modification have separate events and immutable version IDs.                           |
| Games      | Deletion, library removal, package delivery, verified host installation/removal, local/cloud saves, save revision conflicts, scores, sharing/revocation, reports and creator blocks. Payloads include IDs and safe scalar metadata.                                                                          |
| Player     | A play starts only after a validated successful GameSDK exchange. Includes player identity, game/version/creator IDs, first/repeat play, session ID and fixture label. Pause/resume/end events measure foreground time. Load, renderer, runtime and bridge failures are bounded to five reports per session. |
| App        | Open/foreground/background, route-template screen changes, host HTTP response/network failures, handled user-action failures and render boundaries.                                                                                                                                                          |
| Errors     | PostHog `$exception` events for unexpected API 5xx, worker/preflight/generation/maintenance/cleanup and process-fatal errors, player failures, mobile JS uncaught errors/rejections and native crash capture. Expected API 4xx remain failure metrics.                                                       |

Verified Supabase UUIDs are the PostHog distinct IDs on all three services. Mobile identification never includes email, display name or profile contents. The SDK resets its persisted identity at startup and at logout/account changes. A guest uses an anonymous SDK identity; no synthetic shared guest person is created. API requests that cannot be authenticated use a request-scoped anonymous ID with person processing disabled. Worker process failures use a service identity with person processing disabled.

`first_play` means the first successful play of the **current downloaded installation**. Reinstallation or another device can produce another first play. To answer account-wide first-ever play, use the earliest `game_play_started` by distinct ID/game ID. `game_play_ended.active_duration_ms` excludes background time; force quits and crashes may have no end event, so play counts come from starts. Guest IDs cannot identify a real account until sign-in. PostHog runs in the trusted host only; games send a fixed runtime-error notification without analytics credentials or raw error text.

`generation_completed.duration_ms` measures pipeline time, including typed Jev moderation. `total_duration_ms` measures reservation to published signed package, including queue and model-availability preflight. `generation_preflight_started.queue_wait_ms` isolates worker scheduling. Dedicated moderation events measure accepted moderation latency without decision or prompt contents. Stage events attribute elapsed time to `previous_stage`, including repeated repair stages. A reservation is not a published game, and HTTP package delivery is not a successful installation.

## Account delivery and privacy

The Supabase trigger inserts small rows into the private `analytics_outbox`, with stable event UUID, account UUID, event type, confirmation boolean and original timestamp. It does not copy profile data. The worker dispatches up to 100 rows every ten seconds, using a separate SDK without automatic flushing. It acknowledges rows only after delivery succeeds, uses stable PostHog event UUIDs for retries, and locks rows with `SKIP LOCKED` for concurrent workers. Disabled analytics retains rows for later delivery; monitor backlog and ensure a worker runs even if AI generation is disabled. Applying the migration does not backfill pre-existing users.

Properties pass an explicit allowlist. Prompts, save JSON, report text, share/recovery tokens, credentials, emails, request bodies, raw URLs and generated source are excluded. Exception messages are withheld; stack locations and error types remain available for grouping. Both SDKs sanitize exception payloads **after** SDK enrichment, removing source snippets, locals and arbitrary exception metadata. This was verified against the actual Node SDK payload, including SDK-added source context. Session replay, automatic click capture, console capture and exception breadcrumbs are disabled.

Account deletion emits a lifecycle event; it does not erase historical PostHog data. Implement PostHog person/event erasure in the production data-deletion procedure if required by the app's retention policy. No automatic purge or notification recipient is configured by this change.

## Dashboards and error symbols

The Product dashboard covers account growth/logins, requested versus published games, daily active players, first/repeat plays, **who played which game**, foreground engagement, downloads, saves and shares. Reliability covers endpoint counts/p50/p95 latency and 4xx/5xx rates, total generation p50/p95, queue delay, stage timing, outcomes/repairs and errors by operation. Both use a rolling 30-day window and their named environment, excluding explicitly deterministic samples. Error Tracking groups `$exception` events; environment/release/service/operation/game/version IDs support investigation.

Expo's Metro configuration includes PostHog's source-map integration. To upload production JS maps and native symbols, set `POSTHOG_UPLOAD_SOURCEMAPS=true` plus private `POSTHOG_CLI_API_KEY`, `POSTHOG_CLI_PROJECT_ID` and the region host in the build environment. The Expo config plugin enables symbol uploads without disabling Xcode sandboxing. Uploading is opt-in so local/test builds do not require a management key. Build a new native development/release client after installing the native crash plugin; Expo Go and an older installed client cannot verify it. Server deployments should retain/upload their matching source maps with the official CLI if compiling the Node sources.

## Verification status

Unit tests exercise safe delivery, identity, redaction at the real SDK boundary, player timing, endpoint templates/mutation success/error behavior and generation timing/repairs. Integration tests use real Supabase auth and Postgres to check lifecycle events, RLS, stable retry IDs and acknowledgment only after successful delivery. Tests explicitly disable live PostHog traffic, and integration cleanup removes only its own test-account outbox rows. Browser and deterministic fixtures do not prove native crash capture or live provider ingestion. See `docs/TESTING.md` for the latest measured results and blockers.

At implementation time, hosted setup remains blocked by PostHog onboarding/CLI authorization. The plan and setup command are ready, but dashboard creation, live ingestion and production symbol uploads must not be represented as completed until authenticated configuration and delivery are verified.
